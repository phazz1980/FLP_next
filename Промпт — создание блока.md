# Промпт: создать блок для FLP_next

Этот файл — самодостаточное задание для ИИ-агента. Вставьте его целиком в начало диалога
(или дайте агенту путь к файлу в репозитории) и допишите в самом конце раздел **«Задание»**.
Агент должен суметь сделать блок, не задавая вопросов о формате.

---

## 0. Задание (заполняет человек)

```
Блок: <название по-русски>, тип <latin_id>
Группа: <например «Датчики» или «Насосы/Управление»>
Что делает: <одна-две фразы>
Входы:  <имя (bool|int|float|string|any) — смысл; есть ли значение по умолчанию>
Выходы: <имя (bool|int|float|string) — смысл>
Параметры: <имя (bool|int|float|string|duration|pin) — смысл, границы, значение по умолчанию>
Память между циклами: <да/нет>
Железо / библиотека Arduino: <датчик, шина, имя библиотеки или «нет»>
Куда положить: <user_library (по умолчанию) | library (встроенный блок)>
```

Если в задании чего-то не хватает и это нельзя разумно выбрать самому — один раз коротко
спросите. Всё, что есть разумное значение по умолчанию, выбирайте сами и перечислите в отчёте.

## 1. Что такое FLP_next

Программа визуального программирования микроконтроллеров (язык FBD) на Rust: схема из
блоков и связей превращается в скетч Arduino C++ для ESP32 (ESP32, ESP32-C3, ESP32-S3), который
собирает `arduino-cli`. Блок — это **папка с тремя файлами**, расширяемая без перекомпиляции
программы; библиотека подхватывается «на горячую».

Язык общения — русский. Описания блоков, подписи портов и параметров, `docs.md`, тексты ошибок —
**по-русски**. Идентификаторы в коде, имена типов, комментарии в коде и шаблонах — **по-английски**.

Карта репозитория:

| Путь | Что там |
| --- | --- |
| `library/<тип>/` | встроенные блоки (идут с программой) |
| `user_library/[<группа>/…/]<тип>/` | пользовательские блоки того же формата |
| `library/README.md` | полный справочник формата блока (читать обязательно) |
| `examples/<имя>/` | примеры проектов (`project.toml`, `logic.toml`, `layout.toml`) |
| `crates/flp-codegen/tests/snapshots/` | снимки сгенерированного кода по примерам |
| `crates/flp-core/src/pins.rs` | таблицы выводов плат |
| `Архитектура и план.md` | архитектура; читать по разделам, не целиком |

Хорошие образцы для копирования формата: `library/ds18b20` (датчик, библиотеки, `shared`-вывод),
`library/hysteresis` (память, пороги), `library/timer_on` (время, память), `library/scale`
(чистая математика), `library/uart_send` (UART), `library/mqtt_publish` (сеть),
`library/web_button` (виджет веб-интерфейса). Перед созданием блока откройте 2–3 самых похожих.

## 2. Как работать: два пути

**А. Через MCP-сервер `flp`** (если инструменты доступны): `list_block_types` — найти похожие,
`get_block_type` — полное описание (`block.toml`, шаблон, `docs.md`), `create_block_type` —
создать **пользовательский** блок (`type`, `block_toml`, `template`, `docs`). Он проверяет
`block.toml` до записи, отказывает, если тип уже существует (встроенный или свой), и сам
перечитывает библиотеку. Править существующий тип им нельзя — только создавать новый.

**Б. Прямо в файлах** (если работаете в репозитории): создайте папку блока и три файла.
Для пользовательского блока — `user_library/<группа>/<тип>/`, для встроенного — `library/<тип>/`.
Встроенные блоки допускают только осознанные изменения: если задание не просит «встроенный»,
делайте пользовательский.

В обоих случаях тип нельзя занимать повторно: перед созданием проверьте, что имени нет в
`library/` и `user_library/`.

## 3. `block.toml` — полный формат

```toml
[block]
type = "timer_on"            # = имени папки; буквы, цифры, «_», без пробелов и точек
name = "Задержка включения"  # название в редакторе (по-русски)
group = "Время"              # раздел библиотеки; «А/Б» даёт вложенные папки
description = "Одна-две фразы: что делает блок."   # по нему ИИ подбирает блоки — пишите точно
symbol = "TON"               # короткая метка на блоке (по умолчанию — name)
memory = true                # блок хранит состояние между циклами (разрешает обратные связи)
includes = ["DHT.h"]         # #include в начале скетча
libraries = ["DHT sensor library"]  # библиотеки arduino-cli; `flp build` ставит недостающие
single = true                # в проекте может быть только один такой блок (Wi-Fi, NTP)

[[input]]
name = "in"
label = "Вход"               # необязательно: подпись на блоке (можно по-русски, с пробелами)
type = "bool"                # bool | int | float | string | any
default = false              # нет default → вход обязан быть подключён
description = "…"
when = 'source == "input"'   # необязательно: порт существует, пока условие истинно

[[output]]
name = "out"
type = "bool"                # bool | int | float | string (any у выхода нет, default нет)
description = "…"

[[param]]
name = "time"
type = "duration"            # bool | int | float | string | duration | pin
default = "1s"               # нет default → параметр обязателен
min = 0                      # границы для чисел (у duration — в миллисекундах)
max = 100
show = "named"               # подпись под блоком: named («имя=значение», по умолчанию) |
                             # value | secret (звёздочки) | hidden
local = "ssid"               # значение хранится в программе (local.toml), не в файле проекта;
                             # нужны string и default (пароли, ключи)
description = "…"

[[param.choice]]             # выпадающий список; default обязан быть в списке
value = 0
label = "Клиент"

[[param]]
name = "pin"
type = "pin"
mode = "out"                 # io (по умолчанию) | in | out | adc
shared = true                # блоки типа могут делить вывод (шина 1-Wire)
min = -1                     # min < 0: значение -1 = «не используется»

[block.uart]                 # только для блоков на UART, см. раздел 5
param = "port"
access = "write"             # exclusive | write | read | config
```

Правила, которые проверяются при загрузке:

- Имена типов, портов, параметров: буквы (можно русские), цифры, `_`. Входы, выходы и параметры
  **не могут называться одинаково** в пределах блока; `id` и `type` заняты.
- Типы: неявно приводится только `int → float`. `any` — только у входа: принимает любой тип;
  настоящий тип в шаблоне — `{{ input_type.<имя> }}` (`bool`/`int`/`float`/`string`).
  `string` — Arduino `String`, с числами не смешивается (для этого есть блоки группы «Строки»).
- `when` — выражение Jinja над параметрами блока (`duration` — в миллисекундах). Нельзя ссылаться
  на себя и на неизвестный параметр. Отключённого порта нет на схеме и в `input`/`output` шаблона:
  обращайтесь к нему внутри такого же `{% if %}`. Отключённый параметр не обязателен.
- Вход без `default` обязательно подключается, иначе `flp check` даёт ошибку.
- `memory = true` ставьте **всегда**, если блок читает свой выход или хранит что-то между циклами
  (триггер, счётчик, таймер, фильтр, детектор фронта, датчик с кэшем). Цикл в схеме разрешён
  только через блок с памятью.
- Выводы (`pin`) проверяются по плате проекта: несуществующий, флеш-память, не подходящий по
  `mode` → ошибка; UART0/USB → предупреждение; один вывод у двух блоков → ошибка (кроме `shared`).
- Русские имена в коде прошивки транслитерируются автоматически.

## 4. `esp32.cpp.tmpl` — шаблон кода

Шаблон — C++ с подстановками Jinja (minijinja; `{% if %}`, `{% set %}`, `{% macro %}`, фильтры
вроде `|indent`). Разделы отделяются строками-маркерами; любой можно опустить:

| Маркер | Куда попадает |
| --- | --- |
| `// @defines` | `#define` до всех `#include` (например, включение флага библиотеки) |
| `// @global` | глобальные переменные блока |
| `// @functions` | функции блока (стоят перед `setup()`, прототипы не нужны) |
| `// @setup` | в `setup()` |
| `// @loop` | в `loop()`, в порядке исполнения схемы |

Эти разделы повторяются для **каждого экземпляра** блока → все глобальные имена начинайте с
`{{ id }}`. Код, общий для всех экземпляров, — в разделах `once`: `// @global once`,
`// @setup once`, `// @functions once`. Одинаковый текст такого раздела попадает в скетч один раз,
разный — по разу на каждый вариант (например, `OneWire bus_{{ param.pin }}(…)` — одна шина на
вывод). Раздела `// @loop once` нет.

Подстановки:

| Запись | Значение |
| --- | --- |
| `{{ id }}` | id экземпляра блока, префикс его переменных: `{{ id }}_start` |
| `{{ input.<имя> }}` | выражение со значением входа (для неподключённого входа — его `default` литералом) |
| `{{ input_type.<имя> }}` | настоящий тип входа: `bool`/`int`/`float`/`string` |
| `{{ output.<имя> }}` | переменная выхода — ей присваивается значение |
| `{{ param.<имя> }}` | значение параметра как **выражение C++** |
| `{{ value.<имя> }}` | значение параметра как число/строка — для условий: `{% if value.on > value.off %}` |
| `{{ uart.<поле> }}` | настройки UART блока: `serial`, `input`, `number`, `speed`, `config`, `parity`, `rx`, `tx`, `de`, `rx_buffer` |

Как подставляются параметры: `duration` — число миллисекунд (пишите `{{ param.time }}UL`),
`pin` — номер, `bool` — `true`/`false`, `float` — с суффиксом `f` (`2.0f`), `string` — литерал
`String("…")`. Параметр может оказаться привязанным к переменной проекта — значит, `{{ param.x }}`
это не обязательно литерал; не используйте его там, где нужна константа времени компиляции
(размеры массивов, `#if`), и для решений на этапе генерации берите `{{ value.x }}`.

Правила написания шаблонов:

1. **Все глобальные имена с `{{ id }}`.** Иначе два блока одного типа дадут `redefinition`.
2. **`loop()` не блокируется.** Никаких `delay()` и долгих ожиданий: время — через
   `millis()` и переменные состояния (см. `ds18b20`, `timer_on`). Помните про переполнение
   `millis()`: сравнивайте `millis() - start >= period`, а не `millis() >= start + period`.
3. **Выход можно читать в своём же шаблоне** — это значение с прошлого цикла (так сделаны RS-триггер и
   счётчик). До первого цикла выходы равны `false`/`0`.
4. **Инициализируйте** состояние в `@global` или `@setup`.
5. **Читаемость:** над каждым фрагментом генератор ставит комментарий с id блока; свои комментарии
   пишите по-английски, коротко и по делу — как в соседних блоках.
6. Не приводите `string` к числу «неявно»: для этого есть отдельные блоки.
7. Для `any`-входа делайте ветки: `{% if input_type.in == "float" %}…{% elif … %}…{% endif %}`.
8. Нельзя добавлять побочные эффекты, зависящие от порядка блоков, кроме тех, что вытекают из схемы.
9. Безопасные значения по умолчанию: выходы силового управления при ошибке датчика/связи не должны
   «залипать» в опасном состоянии без явного описания в `docs.md`.

Минимальный пример (`scale_clamp`):

```cpp
// @loop
{
  float t = ({{ input.value }} - {{ param.in_min }}) / ({{ param.in_max }} - {{ param.in_min }});
  t = constrain(t, 0.0f, 1.0f);
  {{ output.out }} = {{ param.out_min }} + t * ({{ param.out_max }} - {{ param.out_min }});
}
```

## 5. Блоки на UART

Скорость, формат и выводы UART задаются один раз в настройках платы (`[[uart]]` в `project.toml`).
Блок объявляет `[block.uart] param = "<int-параметр с номером порта>"`, `access = …`:

- `exclusive` — порт настраивает библиотека блока (Modbus RTU); больше никто не использует;
- `write` — блок только отправляет; таких блоков на порту сколько угодно;
- `read` — блок принимает; читатель на порту один;
- `config` — блок сам задаёт настройки порта своими параметрами (`speed`, `format`, `rx`, `tx`, `de`,
  `rx_buffer`).

Номер `-1` — USB (`Serial`, 115200, без настроек). Порты `write`/`read` открывает генератор в начале
`setup()`. Читателю в шаблоне нужен `{{ uart.input }}`, а не `{{ uart.serial }}` (в отладочной
прошивке USB-байты идут через отладку). Доступные UART: ESP32 — 1 и 2, ESP32-C3 — 0 и 1,
ESP32-S3 — 0, 1, 2.

## 6. `docs.md`

Короткая справка по-русски: что делает блок, смысл входов/выходов/параметров, поведение в крайних
случаях (обрыв датчика, переполнение, первый цикл), пример блока в `logic.toml`:

```toml
[[block]]
id = "heater"
type = "hysteresis"
on = 18.0
off = 21.0
```

По `docs.md` и `description` ИИ-помощник потом подбирает блоки, поэтому пишите конкретно, без воды.

## 7. Как проверить (обязательно, не отчитывайтесь без этого)

Для **пользовательского** блока:

1. Создайте проект-пример или возьмите `examples/…`, поставьте блок, подключите входы и выходы.
2. `flp check <проект>` — схема без ошибок (в MCP — `check`).
3. `flp gen <проект> --stdout` (в MCP — `generate`) — прочтите сгенерированный фрагмент блока: нет
   ли дубликатов имён, понятны ли комментарии, верны ли типы.
4. `flp build <проект>` (в MCP — `build`) — скетч компилируется. Показывайте только ошибки и
   предупреждения (`| grep -E "error|warning"`), не весь лог.
5. Если задание касается железа и плата доступна: `flp upload`, затем `flp monitor` или `read_live_values`
   — сравните живые значения с ожидаемыми.

Для **встроенного** блока (в `library/`) дополнительно по правилам репозитория:

- пример проекта в `examples/` с этим блоком — иначе падает тест `every_block_has_an_example`;
  примеры хранятся **папками** (`project.toml`, `logic.toml`, `layout.toml`), не кладите рядом
  `.flpn` с тем же именем (загрузчик предпочтёт его папке);
- снимок генерации: `UPDATE_SNAPSHOTS=1 cargo test -p flp-codegen`, затем просмотрите diff снимка
  **точечно** — нет ли лишних изменений в чужих блоках;
- перед завершением: `cargo fmt`, `cargo clippy -p flp-codegen --all-targets`,
  `cargo test -p flp-codegen -q` (полный прогон workspace — только в конце);
- строка в таблице блоков `library/README.md`, если появилась новая группа.

Экономия контекста: `arduino-cli` без `-v`; не читайте `target/`, `.flp/`, `Cargo.lock`; код
ищите `grep`/`Glob`, большие файлы читайте диапазонами; файл архитектуры — по разделам.

## 8. Типичные ошибки

| Ошибка | Причина и исправление |
| --- | --- |
| «тип занят встроенным блоком» / «уже есть» | выберите другое имя типа |
| `block.toml: …` | формат (тип порта, `default` вне `choice`, `when` на несуществующий параметр) |
| `redefinition of …` при сборке | в `@global`/`@functions` имя без `{{ id }}` (или общий код не в `once`) |
| цикл без блока с памятью | у блока нет `memory = true`, хотя он хранит состояние |
| вход «не подключён» | у входа нет `default`, а он нужен необязательным — задайте `default` |
| схема не принимает связь | типы несовместимы: нужен `int → float` или отдельный блок преобразования |
| `{{ input.x }}` пусто | порт под `when`, а обращение вне такого же условия |
| долгий цикл, «зависание» | `delay()` или блокирующее чтение в `@loop` — переделайте на конечный автомат по `millis()` |
| библиотека не найдена | не указана в `libraries` / нет `includes` |

## 9. Что сообщить в конце

Коротко, по-русски:

1. Какие файлы созданы (пути).
2. Входы/выходы/параметры блока и принятые вами допущения (всё, чего не было в задании).
3. Что проверено и чем (`check`/`gen`/`build`/железо) и что **не** проверено.
4. Если блок управляет силовой нагрузкой или хранит данные во флеш — отдельно отметьте, как он
   ведёт себя при отказе датчика/связи и при перезагрузке.

Не коммитьте и не публикуйте без просьбы. Не удаляйте чужие файлы проекта.

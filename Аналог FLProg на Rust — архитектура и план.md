# Аналог FLProg на Rust — архитектура и план

Oct 23, 2026 · @Анатолий

## Цель и рамки

Своя программа визуального программирования микроконтроллеров в духе FLProg, написанная с нуля на Rust, со встроенным ИИ-помощником, который работает прямо в проектах.

- Программа для себя; публичный выпуск — возможно позже.
- Повторяем функциональность и привычную раскладку FLProg, но код, иконки и графика свои. Исходники FLProg не используются.
- Отличия от FLProg: ИИ-помощник и MCP, текстовый формат проекта, расширение без перекомпиляции.
- Вне первой версии: симулятор, язык LAD, генерация на Rust, отладка по Wi-Fi.

## Формат проекта

Проект — один файл `<имя>.flpn`: обычный ZIP-архив, который открывается любым архиватором. Внутри — TOML-файлы; логика хранится отдельно от координат, чтобы ИИ правил смысл и не трогал картинку.

- `project.toml` — плата, частота, настройки сборки
- `logic.toml` — блоки и связи
- `layout.toml` — координаты блоков, только для редактора
- `boards.pdf` — картинка всех плат (по странице на плату), пересоздаётся при каждом сохранении (крейт `flp-pdf`), чтобы схему можно было посмотреть и распечатать без редактора; пароли в нём скрыты

Сохранение атомарное: архив пишется во временный файл и подменяет старый. Рядом с проектом лежит рабочая папка `.flp/<имя>/` (скетч и кэш сборки), так что в одной папке может быть несколько проектов. Двойной щелчок по `.flpn` открывает редактор после «Файл → Открывать .flpn двойным щелчком» (запись в `HKCU\Software\Classes`, без прав администратора).

Старый формат — папка с теми же тремя TOML-файлами — по-прежнему читается (примеры в `examples/` хранятся так, чтобы их было удобно смотреть в git); при сохранении из такой папки появляется `<папка>/<папка>.flpn`, а `flp convert <папка>` переводит её явно.

Правила:

- Понятные имена блоков (`pressure`, `pump`), а не порядковые номера.
- Связи пишутся как `блок.порт` → `блок.порт`.
- Как в FLProg, на вход вместо связи можно поставить константу, а логический порт — инвертировать (ПКМ по порту в редакторе). В блоке это `const = { b = -0.5 }` (вход → значение; связь на тот же вход константу заменяет), `invert = ["out"]` (выходы: инверсию видят все связи выхода) и `invert_in = ["en"]` (входы). Генератор подставляет значение константы или `!` в выражение входа.
- В файлах можно писать комментарии.
- Проект можно распаковать и поправить даже в блокноте. Комментарии в TOML при сохранении из редактора пока не сохраняются.
- Для обмена с ИИ (API и MCP) те же структуры автоматически переводятся в JSON через serde.

Как это сделано в FLProg (для сравнения): проект `.flp` и блок `.ubi` — XML-сериализация объектов Smalltalk (SIXX) в UTF-16, файлы по 10–70 МБ. Логика там перемешана с состоянием окна (прокрутка, раскрытые ветки дерева, ширина панелей) — ровно то, от чего нас защищает отдельный `layout.toml`. Связь в FLProg — цепь: один выход и список входов плюс трассировка; у нас то же самое выражается несколькими `[[link]]` с одним `from`. Формат читаемый, поэтому импорт проектов и пользовательских блоков FLProg возможен позже.

Пример: насос включается, если давление ниже 2 бар дольше 5 секунд.

```toml
[[block]]
id = "pressure"
type = "analog_in"
pin = 34

[[block]]
id = "low"
type = "less"
b = 2.0

[[block]]
id = "delay"
type = "timer_on"
time = "5s"

[[block]]
id = "pump"
type = "digital_out"
pin = 26

[[link]]
from = "pressure.out"
to   = "low.a"

[[link]]
from = "low.out"
to   = "delay.in"

[[link]]
from = "delay.out"
to   = "pump.in"
```

## Библиотека блоков и расширение

Блок не выполняется внутри программы, он только превращается в код прошивки, поэтому новые блоки добавляются файлами, без перекомпиляции редактора.

### Три уровня расширения

1. **Блоки-файлы** — папка в `library/`:
   - `block.toml` — название, входы, выходы, параметры, описание на русском, переменные для отладки
   - `esp32.cpp.tmpl` — шаблон кода Arduino (позже рядом `esp32.rs.tmpl` для Rust)
   - `docs.md` — пояснение и пример Положил папку — редактор подхватил блок без перезапуска.
2. **Составные блоки** — выделенная часть схемы сохраняется как один блок со своими входами и выходами.
3. **Скриптовые плагины** (Rhai, Lua или WASM) — новые платы, проверки схем, импорт, ИИ-провайдеры. Вторая очередь, но архитектуру закладываем сразу.

Блоку не обязательно иметь оба шаблона: если варианта под выбранную генерацию нет, редактор об этом скажет. ИИ может сам создавать новые блоки-файлы по описанию.

### Доработки формата блока (по опыту FLProg)

В FLProg блок на C (редактор Professional) устроен так же, как наш `block.toml` + шаблон, но решает больше задач. Что берём:

- **Все секции скетча** *(сделано)*. Шаблон понимает `// @global`, `// @setup`, `// @loop` и `// @functions`. Функции блока ставятся перед `setup()`, а не в конец скетча, как у FLProg: так не нужны прототипы.
- **Общий код и код экземпляра** *(сделано)*. Секции с пометкой `once` (`// @global once`, `// @setup once`, `// @functions once`) попадают в скетч один раз на каждый различающийся текст: одна шина OneWire на вывод, одна вспомогательная функция на проект. Остальные секции — на каждый экземпляр.
- **Только один экземпляр** *(сделано)*. `single = true` в `[block]` — проверка схемы ругается на второй экземпляр (Wi-Fi, NTP, глубокий сон).
- **Условия по параметрам** *(сделано)*. `{% if %}` в шаблонах описан в `library/README.md`. У порта и параметра есть поле `when = "<выражение Jinja>"`: порт или параметр есть у блока только при выполнении условия. Отключённых портов нет на схеме и в коде, отключённые параметры не обязательны и скрыты в окне свойств.
- **Редактор блоков** *(сделано)*, в духе FLProg Professional: окно «Редактор блока» (меню «Библиотека → Новый блок…», правая кнопка на блоке в библиотеке или на схеме). Там правятся заголовок, входы, выходы, параметры (с `when`), шаблон кода и `docs.md`. Рядом видно, как блок выглядит на плате, и есть пробная генерация: скетч с одним экземпляром блока (`flp_codegen::preview_block`). Сохраняет `flp_core::save_block`: сначала проверяет описание и перезаписывает только изменившиеся файлы, поэтому комментарии в нетронутом `block.toml` остаются. Если сменить тип, блок сохраняется как новый, а старый остаётся.
- **Встроенные и пользовательские блоки** *(сделано)*. Встроенные лежат в `library/` и не меняются: в редакторе их можно только посмотреть или скопировать. Пользовательские лежат в `user_library/` рядом с `library/`, их пишут редактор блоков и ИИ (`create_block_type`). `Library::load_with_user` читает обе папки, `Library::is_user` / `is_builtin` различают их. Пользовательский блок с типом встроенного пропускается с ошибкой. Свои блоки можно удалить из библиотеки, перед удалением показывается подтверждение.
- **Русские подписи портов и параметров** *(сделано)*. Поле `label` у входа, выхода и параметра: его видно на блоке и в окне свойств. Имена остаются латиницей — это идентификаторы в схеме, шаблонах и C++, а старые версии ESP32-компилятора не принимают кириллицу в именах. В редакторе блока подписи пишутся в колонке «Подпись», а в поле кода по правой кнопке открывается меню подстановок (входы, выходы, параметры, условия, разделы шаблона).
- **Входы как выражения.** FLProg подставляет вместо входа выражение в скобках и сам предупреждает, что не каждая функция библиотеки его переварит. У нас вход — это имя переменной выхода или константа; если генератор начнёт сворачивать арифметику в выражения, шаблон должен иметь способ попросить переменную (`{{ input.x | var }}`).
- **Временные переменные не берём:** у FLProg одна общая переменная на тип ради экономии памяти, это источник ошибок. Блок объявляет свои локальные переменные внутри `{ }` секции `@loop`.
- **`#include` уже собираются в одно место и без повторов.** Добавить `includes_ordered = true` для случая, когда порядок подключения важен.
- **Пакеты блоков и общие параметры** (параметр, общий для всех экземпляров, например скорость шины Modbus) — позже, вместе с Modbus. Пока общие настройки живут в `project.toml` внутри проекта.
- **Учёт выводов** *(сделано)*. У параметра `pin` есть `mode` (io/in/out/adc) и `shared` (общий вывод для блоков одного типа — шина 1-Wire), `min = -1` разрешает «не используется». Таблица выводов ESP32/C3/S3 — `flp-core::pins`, плата определяется по fqbn, а если у платы выведена только часть выводов — по `board.model` (`BOARD_MODELS`: пока `esp32c3_supermini` — ESP32-C3 Super Mini, GPIO0–10, 20, 21). `check_project` ловит повторы, отсутствующие и флеш-выводы, неподходящий режим; UART0/USB — предупреждение. В окне свойств вывод выбирается из списка, занятые недоступны; ИИ видит занятые и свободные выводы в `get_schema`.

### Строки и UART

Тип порта **`any`** (`SignalType::Any`, только у входов): принимает выход любого типа и константу любого вида; генератор подставляет настоящий тип источника в `Input::ty`, шаблон видит его в `{{ input_type.<порт> }}`. Первый пользователь — «Отправка в UART»; дальше пригодится сравнению, переключателям, записи во флеш.

Решено (октябрь 2026), делаем по шагам в таком порядке:

1. **Монитор порта и консоль** *(сделано)* — вкладка внизу рядом с «Сообщениями», см. раздел «Онлайн-отладка».
2. **Тип `String`** *(сделано)* — `SignalType::String`, в TOML `type = "string"`. Неявных преобразований нет: числа в строку и обратно — блоками. В скетче — Arduino `String`, в `setup()` каждой строке `reserve(32)`. В отладке строки — отдельная таблица `DebugTable::texts` и кадр `TEXT` (0x04): индекс и до 64 байт UTF-8 (обрезка по границе символа), только при изменении контрольной суммы, не больше 8 кадров за 100 мс; после `HELLO_REQ` шлются все. Редактор показывает строки в кавычках на проводах, выходах, тегах переменных и в окне «Входы и переменные»; форсировки строк нет. Блоки (группа «Строки»): `text_const`, `num_to_text` (знаков после точки, текст до и после), `text_to_num` (выход `ok`, запятая как точка, при ошибке значение не меняется), `text_concat` (2–4 входа, разделитель), `text_compare` (равна / содержит / начинается / заканчивается, без учёта регистра), `text_length`, `text_substring`. Пример — `examples/text_commands`.
3. **Настройки UART в конфигурации платы** *(сделано)* — `[[uart]]` в `project.toml` (`flp_core::uart`): номер, скорость, формат (`8N1`, `8E1`…), RX, TX, DE/RE для RS-485, буфер приёма; правятся в окне «Настройки МК», там же видно, какие блоки используют порт. UART0 — USB без настроек (115200, только запись). Блок объявляет `[block.uart]` с параметром номера и доступом `exclusive` / `write` / `read`. Проверка: UART есть у платы (у ESP32-C3 только UART1), формат понятен, порт настроен, у порта не два владельца (exclusive — один, read — один читатель), выводы UART не заняты блоками и другим UART. Порты с `write`/`read` открывает генератор в начале `setup()`; шаблоны получают `{{ uart.* }}`. Modbus RTU (`exclusive`) берёт скорость, чётность и выводы из настроек; старые параметры `speed`, `parity`, `rx`, `tx`, `de` блоков Modbus RTU переносятся в `[[uart]]` при загрузке проекта.
4. **Блоки «Отправка в UART» и «Чтение из UART»** *(сделано)*. `uart_send` (доступ `write`, по умолчанию UART0): один вход `value` типа `any` — тип берётся от подключённого выхода; «как отправлять» — текстом (числа цифрами, float с `decimals`, окончание нет/`\n`/`\r\n`) или двоично (bool — байт, int — байт/int16/long, float — 4 байта, строка — её байты); «когда» — по фронту `en`, каждый цикл или по изменению значения (для float — с мёртвой зоной); выход `sent`. Старые `mode`, `edge`, входы `text`/`lvalue` переносятся при загрузке (`uart::migrate_uart_send`). Если в буфере передачи меньше места, чем нужно (но не больше 64 байт), сообщение пропускается — цикл не ждёт. `uart_read` (доступ `read`, UART1/2): строками до разделителя (`\n` с отбросом `\r`, `\r`, свой символ), конец по паузе `timeout`, `max_len`; выходы `line`, `ready` (импульс на цикл), за цикл одна строка; или по байту (`byte`, `new`); всегда `available`. Разбор чисел и команд — строковыми блоками. Пример — `examples/text_commands`.
Позже добавлен блок **«Настройки UART»** (`uart_config`, доступ `config`): тот же набор настроек порта, но в свойствах блока на схеме; с `runtime = true` — входы `new_speed`, `new_format` и `apply` для смены на лету: новый формат перезапускает порт (`end`/`begin` с выводами и буфером из свойств), одна скорость — `updateBaudRate`; выходы `baud` (текущая скорость) и `ok` (формат понят). Порт настраивается в одном месте: `[[uart]]` или один такой блок (`uart::project_uarts` сводит оба источника, проверка ругается на дубль). Блоки UART вынесены в свою группу библиотеки «UART».

**USB отдельно от UART0.** У блоков порт — `port`: `-1` — USB (`Serial`: монитор, отладка), `0`…`2` — аппаратные UART (`Serial0`…`Serial2`). Набор UART зависит от платы (`uart::chip_uarts`): ESP32 — 1, 2 (UART0 — USB-мост), ESP32-C3 — 0, 1, ESP32-S3 — 0, 1, 2; UART0 у C3/S3 настраивается как остальные. Внутри USB — `uart::USB`. Старый `uart = 0` у `uart_send`/`uart_read` означал USB и при загрузке становится `port = -1`.

5. **Ввод в консоли отладки** *(сделано)* — кадр `TEXT_IN` (0x15, хост → плата, до 200 байт в кадре, длинный ввод — несколькими). В отладочной прошивке, если в схеме есть `uart_read` на UART0, модуль отладки держит кольцевой буфер на 255 байт и объект `flp_dbg_input` с `available()`/`read()`; шаблон чтения берёт байты из `{{ uart.input }}` — это `flp_dbg_input` для UART0 в отладке и сам порт в остальных случаях. В обычной прошивке `uart_read` на UART0 читает `Serial`, то есть строки из монитора порта. В консоли отладки строка ввода работает, когда плата на связи и в схеме есть читатель UART0; иначе подсказка объясняет, почему ввода нет.

## Генерация кода и фоновая сборка

**Окружение сборки.** Редактор при запуске ищет `arduino-cli` и, если его нет, предлагает установить через winget; перед обычной (не фоновой) сборкой `flp-build` проверяет ядро платы (`core list`) и при отсутствии докачивает его (для ESP32 с адресом индекса Espressif). Ключ `--jobs` передаётся только если число потоков задано явно — старые версии `arduino-cli` его не знают.

Схема превращается в скетч Arduino C++ и собирается `arduino-cli`; тяжёлые части собираются заранее в фоне, пока ты рисуешь.

- Генератор устроен как общая часть плюс отдельный вывод под язык, чтобы позже добавить Rust.
- Добавил блок с новой библиотекой — редактор сразу собирает её в фоне и кладёт в кэш.
- При заливке остаётся собрать только небольшой модуль самой схемы и скомпоновать прошивку.
- Постоянная папка сборки у каждого проекта, чтобы кэш не терялся; ядро ESP32 кэшируется на все проекты.
- Ошибки фоновой сборки подсвечиваются на схеме сразу.
- Режимы: отладочная сборка (с модулем отладки, без тяжёлой оптимизации) и рабочая.
- Имя переменной — любой текст («Давление в баке»); имя в скетче генератор строит сам: латинские имена-идентификаторы остаются как есть (`var_t`), остальные транслитерируются и получают хэш полного имени (`var_Davlenie_v_bake_1a2b3c`).
- Переменная с флажком «Сохранять в EEPROM» (`retain = true`) хранится в NVS (Preferences, пространство `flp_vars`): восстанавливается в начале `setup()`, а в `loop()` раз в секунду пишется, только если отличается от последнего сохранённого значения. Ключ — хэш имени и типа, так что после смены типа старое значение не читается. Блок `flash_store` тоже пишет во флеш, только если значение изменилось.

Нагрузка на компьютер:

- Низкий приоритет процесса и ограничение потоков; сборка стартует через пару секунд после последней правки.
- Кнопка «Очистить кэш» и выключатель фоновой сборки в настройках.

## Онлайн-отладка по USB

Схема в редакторе показывает живые значения с платы, как в ПЛК; первый транспорт — USB, Wi-Fi добавится отдельным слоем.

Что видно:

- логические линии подсвечены по состоянию, на числовых — текущие значения;
- состояние внутри блоков: отсчёт таймера, значение счётчика;
- график любого сигнала во времени.

Что можно менять:

- уставки (пороги, время таймеров) без перепрошивки;
- форсировка входов и выходов, такие сигналы ярко помечены.

Как устроено:

- в прошивку встраивается отладочный модуль, каждая связь получает номер, плата шлёт значения несколько раз в секунду;
- двоичный обмен с контрольной суммой, служебные пакеты отделены от обычного `Serial.print`;
- редактор сам переключает порт между прошивкой и отладкой, переподключается после обрыва;
- прошивка хранит отпечаток схемы — при несовпадении редактор предупреждает;
- в `block.toml` блок указывает, какие внутренние переменные можно смотреть и какие параметры менять.

ИИ тоже видит живые значения и может по ним объяснить, почему схема ведёт себя не так.

Сделано в первой версии (протокол v1, крейт `flp-debug`):

- кадр `0xAA 0x55 | тип | длина | данные | CRC-16/CCITT`, 115200 бод; байты вне кадров — обычный вывод скетча, редактор показывает их во вкладке «Консоль»;
- наблюдаются выходы блоков и переменные, каждое значение — 4 байта; плата шлёт их раз в 100 мс;
- форсировка применяется сразу после блока, который даёт значение, так что её видят все блоки ниже; уставки — это переменные, которые никто не записывает, их значение пишется командой «Записать один раз»;
- в редакторе входы (выходы блоков с выводом платы) и переменные меняются в окне «Значения» (запись и форсировка), из контекстного меню на схеме и в дереве тегов; там же видны живые значения;
- отпечаток — FNV-1a по таблице наблюдаемых значений; при несовпадении значения не показываются;
- модуль встраивается только в отладочную сборку (`flp build --debug`, кнопка «Отладка» в редакторе); `flp monitor` показывает значения в консоли;
- пока нет: внутренние переменные блоков из `block.toml` (отсчёт таймера) и изменение параметров блоков на лету — сейчас для этого служат переменные.

**Диагностика времени цикла.** В прошивке модуль `flp_st_*`: замер всего цикла логики и каждого листа
(метка `flp_st_sheet(k)` там, где порядок выполнения переходит на блоки другого листа), фиксация максимумов.
В отладке — кадр `STATS` (0x03) раз в 0,5 с, сброс максимумов командой `RESET_STATS` (0x14), окно «Диагностика».
В обычной прошивке включается в `project.toml`: `[diagnostics] enabled = true, interval_ms = 5000` — отчёт текстом в Serial.

**Монитор порта и консоль.** Вкладка «Монитор порта» внизу, рядом с «Сообщениями», работает в двух режимах:

- без отладки — обычный монитор: сам открывает порт (тот же, что для заливки) на выбранной скорости, показывает весь текст и отправляет строку с выбранным окончанием (нет, `
`, `
`); кнопка «Подключить/Отключить». Если в прошивке есть модуль отладки, его кадры отбрасываются тем же парсером;
- в отладке — консоль: порт держит сеанс отладки, вкладка показывает текст прошивки (`Serial.print`, отчёт `[FLP]`); строка ввода отправляет текст кадром `TEXT_IN` блоку «Чтение из UART» на UART0.

Порт держит кто-то один: перед заливкой и на время отладки монитор отдаёт порт и потом подключается снова. Общее: автопрокрутка, пауза, очистка, метки времени, фильтр, буфер на 5000 строк. В «Сообщения» вывод платы больше не попадает.

## ИИ-помощник и MCP

У ИИ два входа — чат в редакторе и MCP-сервер, и оба вызывают один и тот же набор команд, так что логика пишется один раз.

&#91;embedded content: как ИИ подключается к программе\]

- **Провайдеры**: Claude по умолчанию; общий интерфейс позволяет подключать OpenAI, локальные модели через Ollama и другие, указав ключ в настройках.
- **Правки с предпросмотром**: ИИ предлагает изменения, они подсвечиваются на схеме, ты принимаешь или отменяешь.
- **Описания блоков** на русском — по ним ИИ подбирает блоки под задачу.
- **Работа без редактора**: через MCP можно собрать схему, прошить плату и потом открыть результат в редакторе.
- **Что умеет**: собрать схему по описанию, объяснить чужую схему, найти ошибки, создать новый блок, разобраться в поведении по живым значениям.

Сделано в первой версии:

- `flp-ai` — 18 команд с JSON-схемами (чтение схемы и библиотеки, правка блоков, связей, параметров и переменных, проверка, генерация, сборка, заливка, живые значения, создание типа блока). Каждая правка — всё или ничего, ответ содержит результат проверки.
- Провайдер — трейт `Provider`; реализован Claude через Messages API (сырой HTTP, официального SDK для Rust нет). Модель по умолчанию `claude-opus-5-5`, меняется переменной `FLP_AI_MODEL`; ключ — `ANTHROPIC_API_KEY`. При отказе по правилам безопасности запрос автоматически повторяется на запасной модели (`fallbacks: "default"`).
- Второй провайдер — `OpenAiCompat` (модуль `openai`): любой OpenAI-совместимый `chat/completions` (роутеры, OpenRouter, локальные серверы). Включается переменной `FLP_AI_BASE_URL` (например `https://host/v1`), плюс `FLP_AI_KEY` и `FLP_AI_MODEL`; без `FLP_AI_BASE_URL` работает Claude. История остаётся в формате Messages API, преобразование в обе стороны — на границе провайдера (`tool_use` ↔ `tool_calls`, `tool_result` ↔ сообщение `role: tool`).
- В редакторе вкладка «ИИ-помощник»: ИИ работает в фоне на копии проекта, каждая его правка — отдельный шаг отмены (Ctrl+Z). Предпросмотра правок с подсветкой пока нет.
- `flp-mcp <файл проекта .flpn>` — MCP-сервер по stdio. Перед каждой командой перечитывает проект с диска, после правки сохраняет. Подключение в Claude Code: `claude mcp add flp-next -- D:\FLP_next\target\debug\flp-mcp.exe D:\путь\к\проекту.flpn`; в Claude Desktop — запись в `claude_desktop_config.json` с теми же командой и аргументом.
- `flp-web <проект> [--port 8080]` — крошечный HTTP-сервер на std (только 127.0.0.1, проверка Host и JSON-типа против чужих страниц): отдаёт страницу конструктора веб-интерфейса (ниже) и `POST /api/<команда>` в тот же набор команд `flp-ai`. Запросы обрабатываются по одному. Веб-редактор схемы убран: схемы правятся в egui-редакторе.
- **Конструктор веб-интерфейса ESP32** (`flp-web`, адрес `/`, он же `/designer`). Веб-страница управления живёт в прошивке: блок `web_ui` (один на проект) регистрирует обработчики `/ui`, `/ui/layout`, `/ui/state`, `/ui/set` на веб-сервере блока Wi-Fi (общая ссылка `flpWebSrv`), а виджеты — блоки группы «Веб-интерфейс» (`web_button`, `web_switch`, `web_slider`, `web_input`, `web_led`, `web_value`, `web_gauge`, `web_text`, `web_label`) — регистрируют себя в общем реестре `FlpUiItem` (подпись, единицы, клетка сетки 12 колонок, значение). Управляющие виджеты пишут в выход блока, индикаторы читают вход; страница (один HTML в `PROGMEM`, около 4 КБ) опрашивает `/ui/state` дважды в секунду. Конструктор в `flp-web` — те же команды `flp-ai` (`add_block`, `set_params`, `connect`): сетка с перетаскиванием и изменением размера, подписи/единицы/диапазоны, привязка входов виджета к выходам схемы, предпросмотр в iframe той самой страницы (переключателем «Редактор / Предпросмотр») (она берётся прямо из шаблона `library/web_ui/esp32.cpp.tmpl`, ответы `/ui/*` подставляются локально). Страницы: названия — параметр `pages` блока `web_ui` («Главная;Насос»), виджет относится к странице параметром `page`; на устройстве слева меню страниц (200 px с подписями, до 900 px — узкая полоска с буквами, до 600 px — полоса сверху), в конструкторе вкладки страниц; виджеты создаются только в редакторе (конструктор без палитры шаблонов), конструктор подхватывает их сам раз в 2 с. В редакторе (левая панель, секция «Веб-интерфейс») страницы добавляются, переименовываются и удаляются списком, виджеты сгруппированы по страницам; «Добавить виджет» открывает окно «Новый виджет» (тип, страница и параметры типа: подпись, единицы, диапазон, шаг), в свойствах существующего виджета страница выбирается из списка, а расположение и размер не показываются — они задаются в конструкторе. **Пароль**: параметр `password` блока `web_ui`; страница `/ui` открыта, все `/ui/*` требуют `?k=<пароль>` (иначе 403), клиент хранит ключ в `localStorage` и показывает форму входа (пароль по обычному HTTP, не шифруется). **Графики**: `web_chart` — кольцевой буфер в ОЗУ (`points`, период `period` с), история отдаётся `/ui/hist`, пропадает при перезагрузке. **Пассивные элементы**: `web_shape` (линия, вертикаль, прямоугольник, круг; толщина). **Цвета**: у каждого виджета `color` и `back`, у страницы `bg` блока `web_ui`; в конструкторе — выбор цвета и список форм. **Страница «Система»** (параметр `system`): `/ui/info` — IP, MAC, сигнал, аптайм, чип, память, флеш, сборка; прошивка по воздуху через приёмник блока Wi-Fi (`POST /update`, нужен флаг `web_update`; `FLP_WEB_UPD` сообщает `web_ui`, что он есть). **Настройки сети**: `web_net` — форма Wi-Fi (SSID, пароль) и адреса (DHCP, IP, шлюз, маска) для Wi-Fi/Ethernet; сохраняется во флеш (Preferences), при наличии `web_net` генератор подставляет в блоки Wi-Fi/Ethernet значения из общей структуры `flpNet` вместо их параметров сети (режим «из переменных»: применяются на лету при сохранении формы); пустой пароль в форме = не менять. Форма также настраивает свою точку доступа (SSID, пароль) и режим (клиент / точка / оба), применяются на лету; заглушка `/` в блоках Wi-Fi и Ethernet удалена — страницу отдаёт только `web_ui`. Сканирование сетей: кнопка в форме, `/ui/scan` (асинхронно, список с уровнем сигнала, выбор подставляет SSID). Режим «Клиент, при отсутствии связи — точка»: если клиент не подключён дольше заданной задержки (по умолчанию 30 с), включается точка (режим «оба»), через 10 с после успешного подключения клиента точка выключается; применяемый режим — `flpNet.eff`. **Проверка Wi-Fi-полей**: SSID до 32 байт без управляющих символов; пароль пуст (открытая сеть), 8–63 печатных ASCII-символа или ровно 64 hex; проверяет `flp check` для блока `wifi` (`wifi_text_error` в `flp-core`), форма в браузере и прошивка `web_net` (неверное значение не сохраняется). Не сделано: проверка на плате (собирается для ESP32-C3, на устройстве не запускалась).
- Блоки логики по справке FLProg: группы как в справке (Базовые элементы, Масштабирование, Триггеры, Таймеры, Счётчики, Математика, Алгебра, Сравнение, Переключатели, Строки, Преобразование типов, Операции с битами, Побитовые операции, Прочее); `mux`, `dms`, `and`, `or`, `xor`, `text_concat` до 16 входов (`count`). Ещё нет: терминал, таблица состояний, массивы, структуры, таблица кодов, секвенсоры (нужны новые типы данных), счётчик на прерываниях (это железо).
- Пока нет: OpenAI и Ollama (точка расширения — `Provider`), сохранение комментариев TOML при правках из MCP.

## Привязки к переменным и служебные блоки

- Порт или параметр (текст, целое, число) блока можно взять из переменной проекта без блоков на листе: `[block.bind]` в `logic.toml` (`порт = "переменная"`). Вход читает переменную, выход пишет в неё после блока, параметр подставляется из неё. Типы должны совпадать; проверка — в `flp-core::check`.
- Блоки с `hidden = true` в `block.toml` (wifi, ethernet, web_ui) — служебные: на листах не рисуются и не предлагаются в библиотеке; ими управляют секции левой панели «Wi-Fi», «Ethernet», «Веб-интерфейс» (галочка включения = наличие блока, у каждого порта и параметра кнопка «→ переменная»).
- В конструкторе веб-страницы привязок к переменным нет — только виджеты; связь с платой идёт через переменные служебных блоков.
- ИИ и MCP: команда `bind` (block, name, variable|null).

## Интерфейс редактора

Общая раскладка повторяет FLProg; детали подгоняем по ходу работы.

- Сверху — меню и панель инструментов: компиляция, загрузка, отладка.
- Слева — дерево проекта и теги: входы, выходы, переменные.
- Справа — библиотека элементов по папкам и вкладка ИИ-помощника.
- В центре — рабочее поле, разбитое на пронумерованные платы-листы.
- Обновления: при запуске (и из «Справка → Проверить обновления») редактор читает GitHub Releases репозитория (`phazz1980/FLP_next`, свой адрес — `update_repo` в `editor.toml`; для закрытого репозитория токен из `FLP_GITHUB_TOKEN` или `gh auth token`), только уведомляет: ссылка в строке состояния и окно «Доступно обновление» со списком изменений (заметки всех релизов новее установленной версии, краткие пункты). Версия показана справа в строке состояния. Кнопка «Обновить и перезапустить» (если рядом с exe есть `library/`): скачивает zip релиза во временную папку, распаковывает (срезая верхнюю папку), сохраняет несохранённый проект, запускает копию exe с `--apply-update`; та ждёт закрытия редактора, переносит заменяемое в `.update_backup`, копирует новое (при сбое возвращает старое), снова запускает редактор; итог пишется в журнал. `user_library`, настройки и проекты не трогаются.

Как это выглядит в FLProg 8.2 (сверено с работающей программой):

- **Меню:** «Файл / Вид / Проект / Инструменты / Настройки / Помощь».
  - «Проект»: «Проверить» (сообщение «Проект корректен» или список ошибок), «Просмотр кода проекта» (окно со сгенерированным скетчем), «Компилировать», «Сменить контроллер», «Обзор схемы».
  - «Инструменты»: монитор COM-порта, запись кодов ИК-пульта, шины данных, установка часов реального времени, запуск Arduino IDE, редактор описаний контроллеров.
- **Под меню:** панель инструментов, вкладки открытых проектов, строка пути «Дерево проекта / Контроллер 1 (…)».
- **Слева, «Дерево проекта»:** контроллер → настройки контроллера, теги, блоки пользователей, коммуникации. Панель сворачивается в вертикальную полоску.
- **Справа, «Библиотека функциональных блоков»:** вкладки «Встроенные» и «Пользовательские», дерево групп с иконками; сворачивается в вертикальную полоску. Над ней — сворачиваемая панель тегов.
- **Центр:** платы идут столбиком; у каждой шапка «Плата: N / Наименование / Комментарии» и индикатор состояния. Над полем — масштаб и вставка платы.
- **Снизу:** имя выбранного контроллера.
- **Мультипроект:** в одном проекте несколько контроллеров, связанных через коммуникации. У нас — позже, когда появится обмен между платами.

Что делаем иначе: вкладка ИИ рядом с библиотекой; монитор порта — вкладка внизу, а не отдельное окно, и в отладке он становится консолью.

Иконки и графика свои, интерфейс на русском.

## План работ

Каждый этап даёт работающий результат; начинаем с ядра без графики.

1. **Ядро** — формат проекта, загрузка блоков из библиотеки, проверка схемы, генерация скетча, сборка и заливка через arduino-cli. Схему можно писать в TOML вручную или просить ИИ.
2. **Базовые блоки** — набор первой очереди с шаблонами Arduino C++.
3. **Редактор** — egui, раскладка как в FLProg, рисование схем на платах-листах.
4. **Онлайн-отладка** — модуль в прошивке, обмен по USB, живые значения, уставки, форсировка.
5. **ИИ-помощник и MCP** — общий набор команд, чат в редакторе, MCP-сервер, подключаемые провайдеры.

Потом: генерация Rust, LAD, Wi-Fi-отладка, скриптовые плагины, блоки второй очереди, импорт проектов и блоков FLProg, несколько контроллеров в одном проекте.

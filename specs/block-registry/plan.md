# Каталог наборов блоков — план

## Границы
`flp-core` не ходит в сеть: он разбирает индекс, сверяет хеш, решает зависимости и ставит наборы из байтов. Скачивание (`ureq`, уже есть в `flp-editor`) делает редактор и передаёт байты ядру. Так всё проверяется тестами без сети.

## Формат
- `pack.rs`, `PackInfo`: добавить `id` (`автор/имя`), `format` (сейчас `1`), `requires` (список `{ id, min_version }`). Обратной совместимости нет, как и в спеке `block-packs`: существующие наборы правятся один раз вручную.
- Новый модуль `flp-core/src/registry.rs`:
  - `Index { packs: Vec<IndexEntry> }`, `IndexEntry { id, name, description, author, license, version, url, sha256, requires }`; `Index::parse(&str)`.
  - `verify_sha256(bytes, expected)` — зависимость `sha2`.
  - `updates(installed, index) -> Vec<Update>` — сравнение целых версий.
  - `resolve(index, installed, wanted_id) -> Result<Vec<IndexEntry>, ResolveError>` — порядок установки с зависимостями; ошибки: нет набора, нет зависимости, цикл, версия ниже требуемой.
  - `dependents(installed, id)` — кто зависит от набора (для предупреждения при удалении).
- `PackImport::from_files` отклоняет набор с неизвестным `format`.

## Редактор
- Настройка `registry_url` (запасное значение — константа; организацию вписать после создания).
- Окно «Каталог» в окне пользовательской библиотеки: загрузка индекса в фоновом потоке, поиск, карточка набора, «Установить», «Проверить обновления», «Обновить».
- Установка: фоновая загрузка всех файлов из `resolve` → `verify_sha256` → `install`. Если что-то из списка не прошло проверку, не ставится ничего (сначала скачиваем и проверяем все, потом ставим).
- Удаление набора предупреждает по `dependents`.

## Риски
- Чужой C++ и Arduino-библиотеки попадают в сборку: поэтому окно показывает состав набора до установки, а публичное открытие каталога ждёт `block-signing`.
- `sha256` в индексе защищает от подмены файла, но не от злонамеренного автора.
- Версии зависимостей только «не ниже»; конфликты диапазонов не решаем.

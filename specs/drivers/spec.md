# Нативная часть блока и скриптовые блоки (драйверы)

Продолжение `specs/wasm-on-mcu/` и `specs/wasm-schema-output/`. Сейчас блок с железом — это C++-шаблон
(`library/<блок>/esp32.cpp.tmpl`), который подставляется в общий скетч: любая правка означает сборку и прошивку всей платы.
Здесь блок получает две независимые части реализации: **нативную** (C++, встроена в мастер-прошивку) и **логику**
(скрипт или WASM, заливается модулем без прошивки). Отдельного «драйвера» нет: драйвер — это нативная часть блока.

## Цель
Новый или изменённый блок логики попадает на плату без прошивки. Полная прошивка нужна только при смене нативной части.
Блок с железом (датчик, шина, библиотека Arduino) пишется на обычном C++ в том же редакторе блока, что и блок с логикой.

## Модель блока
- `block.toml` — интерфейс: входы, выходы, параметры, описание (как сейчас).
- `native.cpp` — необязательная C++-часть, один файл, встраивается в мастер. Описание — в самом файле: заголовок
  `// crab:native ...` (библиотеки Arduino, ресурсы: пины, шина, адрес), `CRAB_INIT(params)`, `CRAB_STEP(in, out)`,
  заглушка для симуляции `// crab:sim ...`. Состояние хранится на каждый экземпляр блока, параметры (пин, адрес) приходят в `init`.
- `logic.crs` (или `block.wasm`) — необязательная логика на небольшом Си/Rust-подобном языке; компилируется в WASM
  собственным компилятором (крейт `crab-script`) с понятными русскими ошибками.
- Варианты: только `native.cpp` (мастер вызывает `step` каждый цикл — как нынешние C++-блоки, но код в мастере); только
  `logic.crs` (блок без железа); оба (скрипт вызывает функции нативной части через `uses`) — второй шаг.
- `esp32.cpp.tmpl` продолжает работать; блоки переводятся на `native.cpp` постепенно (DHT22, DS18B20, Modbus, MQTT).

## Сценарии
1. Пользователь правит `logic.crs` блока и жмёт «залить»: меняется только модуль листа (около секунды).
2. Схема использует блок, чьей нативной части нет в мастере на плате: проверка сообщает по-русски, какого блока нет и что
   нужна сборка мастера.
3. Пользователь создаёт в редакторе блока датчик I²C: выбирает шаблон по типу подключения, правит `native.cpp`, собирает
   мастер для проверки, затем добавляет блок в схему. Два датчика на разных пинах — два экземпляра одного блока.
4. ИИ по описанию датчика или даташиту создаёт интерфейс, `native.cpp` и при необходимости `logic.crs`; пользователь
   проверяет и правит руками.
5. Ручные правки C++ не теряются: редактор читает и пишет сам файл.
6. Готовый код из примера библиотеки вставляется в `native.cpp` без отдельного описания.

## Критерии готовности
- Блок на скрипте проходит `crab-sim` и на плате даёт те же выходы (сверка как у встроенных блоков).
- Мастер собирается из нативных частей блоков проекта; список входит в отпечаток прошивки, редактор показывает, что
  доступно без перепрошивки.
- Блок с `native.cpp` (I²C-датчик на заглушке) собирается в `arduino-cli`, два экземпляра работают независимо.
- Права `allow` в `module.toml` содержат блоки с нативной частью ровно из `uses` листа.

## Вне задачи
Подпись и каталог; динамическая загрузка C++ без прошивки; отладчик скриптов; полный Rust или Си (только небольшое
подмножество: переменные, условия, циклы, функции, bool/int/float); вызов нативных функций из скрипта (`uses`) — второй шаг;
строки (`string`) в нативной части — второй шаг (см. «Решено», п. 8).

## Решено (06.11.2026)
1. Язык логики — синтаксис ближе к Rust/Си (не ST): `let`, `if`/`else`, `while`, `fn`, `bool`/`int`/`float`; входы, выходы,
   параметры и состояние доступны по именам. Компилятор свой (`crab-script`), без внешнего rustc у пользователя.
2. Мастер собирается под проект из нативных частей его блоков; список — в отпечатке прошивки.
3. ИИ-режим — после формы; формат и команды ИИ (создать блок, создать нативную часть) закладываем сразу.
4. Существующие C++-блоки переводятся постепенно, пока остаются как есть.
5. Заливка модуля по USB (`upload-wasm`) уже сделана, эта спека идёт следом.
6. Нет отдельного раздела «Конструктор драйвера»: нативная часть — вкладка редактора блока (тот же C++-редактор, заголовки,
   подсветка, пробная генерация); шаблоны по типу подключения (GPIO/1-Wire, I²C с таблицей регистров, SPI, UART/Modbus,
   библиотека Arduino) — кнопки «Создать по шаблону».
7. Нативная часть — один `native.cpp` с аннотациями; отдельного TOML нет. Начинаем с `CRAB_STEP`; вызовы функций из скрипта
   (`CRAB_EXPORT`, `uses`) — второй шаг.
8. Порты и параметры нативной части — только `bool`, `int`, `float` (время и пин — `int`). Строки (`string`) добавим вторым
   шагом, когда дойдём до блоков с текстом (Wi-Fi, MQTT, UART): структуры `In`/`Out`/`Params` генерируются из `block.toml`, так что
   формат и готовые `native.cpp` не меняются, расширяется проверка `check_interface` и генератор структур. Открыто к тому времени:
   буфер строки (общий в памяти модуля, как в `specs/wasm-io/strings.md`, или копия на шаг), размер и обрезание, `crab:sim` для
   текста. Типы `any`/`number`/`same` в нативной части не планируются.
9. Скриптовый язык (`crab-script`, `logic.crs`) отложен, не отменён. Нативная часть блока — это датчики, шины и библиотеки: они выдают
   данные, а логика строится блоками схемы, и менять её на лету у датчика не нужно. Для своей логики остаётся путь «блок на любом языке
   в WASM» (`block.wasm`). Вызов нативных функций из скрипта (`CRAB_EXPORT`, `uses`) откладывается вместе со скриптом. Возвращаемся к
   нему, если блоки схемы и WASM окажутся неудобны.

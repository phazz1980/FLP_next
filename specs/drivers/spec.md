# Драйверы, скриптовые блоки и конструктор драйвера

Продолжение `specs/wasm-on-mcu/` и `specs/wasm-schema-output/`. Сейчас пользовательский блок — это C++-шаблон
(`library/<блок>/esp32.cpp.tmpl`), поэтому любой такой блок означает сборку и полную прошивку. Здесь логика блока и
работа с железом разделяются: логика становится скриптом и грузится на плату как модуль, а железо — драйвером на C++
в мастер-прошивке.

## Цель
Новый или изменённый блок логики попадает на плату без прошивки. Полная прошивка нужна только при добавлении
нового драйвера. Драйвер — обычный C++, его можно написать руками или создать конструктором (в том числе с помощью ИИ по даташиту).

## Сущности
1. **Драйвер** (`drivers/<имя>/driver.cpp`) — один C++-файл, встраиваемый в мастер. Всё описание — в самом файле: заголовок
   `// crab:driver ...` (имя, библиотеки Arduino, ресурсы: пины, шина, адрес), `CRAB_INIT()`, функции `CRAB_EXPORT` (имя, типы
   `bool`/`int`/`float` аргументов и результата), заглушки для симуляции `// crab:sim ...`. Редактор разбирает файл сам; отдельного TOML нет.
2. **Скриптовый блок** — `block.toml` + тело на небольшом Си/Rust-подобном языке (`logic.crs`). Компилируется в WASM
   собственным компилятором (крейт `crab-script`) с понятными русскими ошибками. Поле `uses = ["драйвер"]` добавляет нужные права в `module.toml`.
3. **Конструктор драйвера** — раздел редактора: шаблон по типу подключения (GPIO/1-Wire, I²C с таблицей регистров,
   SPI, UART/Modbus, библиотека Arduino), форма, предпросмотр кода, сборка мастера для проверки.
4. **ИИ-режим конструктора** — пользователь описывает датчик или вставляет даташит, ИИ заполняет форму и код; результат
   показывается в той же форме и правится руками. Использует общий набор команд ИИ (создать драйвер, создать блок).

## Сценарии
1. Пользователь правит `logic.crs` блока и жмёт «залить»: меняется только модуль листа (около секунды).
2. Схема использует блок, чей драйвера нет в мастере на плате: проверка сообщает по-русски, какого драйвера нет и что
   нужна сборка мастера.
3. Конструктор создаёт драйвер датчика I²C по таблице регистров, собирает мастер, затем создаёт заготовку блока.
4. ИИ по описанию датчика собирает форму конструктора; пользователь проверяет и принимает.
5. Правки C++ вручную не теряются при повторном открытии драйвера в конструкторе: он читает сам `driver.cpp`.
6. Готовый C++-код из примера библиотеки вставляется в `driver.cpp`, добавляются `CRAB_EXPORT`-функции, и драйвер виден скриптам.

## Критерии готовности
- Блок на скрипте проходит `crab-sim` и на плате даёт те же выходы (сверка как у встроенных блоков).
- Мастер знает свой список драйверов (отпечаток); редактор показывает, что доступно без перепрошивки.
- Драйвер, созданный конструктором (I²C-датчик на заглушке), собирается в `arduino-cli` и виден модулю.
- Права `allow` в `module.toml` содержат драйверы ровно из `uses` блоков листа.

## Вне задачи
Подпись и каталог драйверов; динамическая загрузка драйверов (C++) без прошивки; отладчик скриптов; полный
Rust или Си (только небольшое подмножество: переменные, условия, циклы, функции, bool/int/float).

## Решено (06.11.2026)
0. Драйвер — один `driver.cpp` с аннотациями (`// crab:driver`, `CRAB_INIT`, `CRAB_EXPORT`, `// crab:sim`), встраивается в мастер как есть; `driver.toml` не нужен.
1. Язык скриптов — синтаксис ближе к Rust/Си (не ST): `let`, `if`/`else`, `while`, `fn`, типы `bool`/`int`/`float`,
   входы, выходы, параметры и состояние блока доступны по именам, вызовы драйверов как `драйвер.функция(...)`.
   Компилятор свой (`crab-script`), без внешнего rustc у пользователя.
2. Драйверы собираются под проект: мастер строится из нужных проекту драйверов, список драйверов — в отпечатке прошивки.
3. ИИ-режим конструктора — после формы; формат драйвера и команды ИИ (создать драйвер, создать блок) закладываем сразу.
4. Существующие блоки на C++-шаблонах (DHT22, DS18B20, Modbus, MQTT) переводятся на драйверы постепенно, пока остаются
   как есть в обычном скетче.
5. Порядок: заливка модуля по USB (`upload-wasm`) уже сделана, эта спека идёт следом.
